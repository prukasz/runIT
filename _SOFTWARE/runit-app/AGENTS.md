# runit-app

The runIT app, written from scratch. So far: the VM engine in `src/engine/` (read `src/engine/ENGINE.md` first) the link to the board in `src/backend/` (`src/backend/BACKEND.md`), the UI kit in `src/ui/` and `design/`, and the app in `src/app/` (its frame, the connection, Run and Stop, the open project, the Project screen, the Devices view, the Code view (variables, blocks and their canvas), Run with its live view and the Console), in a browser or as the desktop app in `electron/` (below).

## Rules

- **Facts come from the firmware.** The C in `runit-esp/components/vm/` is the truth; `generated/` (in this folder; the bundle `templates/generate_bundle.py` copies from `runit-esp/components/`) is what the app reads. Never a number or layout you cannot point to in C or in a descriptor: put the source in a comment, and a test that reads the C where it can.
- **The backend has no UI** and takes every number of the link from `generated/common/` and every command from the descriptors in `generated/services`, `generated/contracts` and `generated/devices` (`src/backend/definitions.ts` is the only file that reads `generated/`). No service, contract, command or field is named in its code: a new descriptor works with nothing to edit. The engine does not depend on it.
- **The engine has no UI, no DOM, no connection.** It is data in, data out, with its dependencies pointing down `wire` → `catalog` → `model` → `graph` → `expression` → `compiler` → `recover`. The only file that reads `generated/` is `src/engine/generated/index.ts`.
- **A mistake in a project is a diagnostic, not an exception.**
- Aliases: `@engine/*` is `src/engine/*`, `@generated/*` is `generated/*` (see `tsconfig.json`, `vitest.config.ts`).

## The app's frame

`npm run dev` serves the app at `http://localhost:5180` (a fixed port; localhost is a secure context, so Web Bluetooth works; Chrome or Edge). `npm run build` typechecks and builds it. **A devkit board** (firmware built with `CONFIG_RUNIT_BOARD_DEVKIT`): `npm run dev:devkit` (port 5181) or `npm run app:devkit`. It is the same app with `VITE_RUNIT_BOARD=devkit` (`.env.devkit`), so `bundledBoard()` gives `board_devkit.json`: only the ESP pins as device 0, no chips, no power rails or monitor. The window title says `runIT (devkit)`. A hot reload of `App.tsx` or of a backend file makes `useLink` a new link that is not connected while the screen still shows the old state (commands fail "not connected"): reload the page. Vite caches the imported `generated/` descriptors: after `templates/sync.sh` changes them, `touch` the changed JSON files (or restart `npm run dev`) and reload. The desktop app takes Chromium switches after `--`: `npm run app -- --remote-debugging-port=9345` lets a script drive it over the DevTools protocol.

Tested in `tests/app/settings.test.ts`. |

## The Code view

`src/app/code/`: the program (the engine's `Variable` tree and `BlockInstance` list in `ProjectFile.program`) and where its blocks sit on the canvas (`ProjectFile.canvas`), edited through the project, so every change is an undo step. The left panel switches between the variables' tree and the block palette (`runit.code.palette`); the centre is the details (the variables, or the blocks, by that switch) or the canvas; the right panel shows the selected block, else the selected variable. On the canvas a selection opens nothing (the panel would cover the blocks being linked): an open panel follows the selection, and a double-click on a block or the toolbar's pencil (Edit) opens it, or hides it when it shows that block; opening it moves the view just enough that the selected block stays in sight. In the details the panel opens with the selection. A variable picked in the tree stays picked while a block is selected: one click on a pin (or the formula's button) puts it there; a variable picked in the centre opens its own details. The action bar of Code adds, for touch as much as for the mouse: Select (the canvas only: a drag draws a box, as with Shift), Copy, Paste, Edit (the pencil) and Remove.

## The desktop app

The same page in Electron's Chromium, so the board is found and opened again with no browser flags and no chooser. `npm run app` opens it on the Vite dev server (hot reload; an `npm run dev` already running is reused), `npm run app:start` on the built page, `npm run app:dist` builds the Windows installer into `release/` (`electron-builder.yml`). One instance runs per profile (a second launch brings the window forward: two instances on one profile would lose the page's storage); the dev app has its own profile (`<userData>-dev`), so it runs beside the installed one and remembers its own board. Both launchers go through `electron/start.mjs`, which drops `ELECTRON_RUN_AS_NODE` (a terminal in VS Code sets it, and Electron would start as plain Node). Where Windows refuses to rename folders under `Documents` (Controlled folder access) the build fails with `EPERM … rename win-unpacked.tmp`: build into another folder, `npm run app:dist -- -c.directories.output=<path>`.

| File | What |
|---|---|
| `electron/main.mjs` | The window (never throttled in the background: `backgroundThrottling: false` and the Chromium switches against background and occluded-window throttling, so the link's timers and the dead-man's heartbeat keep their pace behind another window) and the board chooser. Electron has none: `requestDevice()` fires `select-bluetooth-device` with every scan result until it is answered. The page names the board to pick when the scan sees it (`ble:want`), or gets the scan (`ble:devices`) and answers with the user's choice (`ble:select`, '' cancels). `ble:gesture` runs `globalThis.__runitGesture` with a user gesture (`executeJavaScript(…, true)`), so `requestDevice()` runs at start with no click. |
| `electron/preload.cjs` | `window.runitDesktop`, the page's side of those messages |
| `src/app/desktop.ts` | `desktop` (undefined in a browser) and `withGesture` |

The page tells the two apart only in `useLink.ts`: on the desktop it remembers the scan's id of the board (`scanId`, the address, which is not the page's `BluetoothDevice.id`), picks it when the scan sees it (gives up after 20 s with "not found nearby"), and with no board remembered the connection panel lists the boards nearby. With **Connect automatically** the app opens the board when it starts and after a reload. The page is loaded from a file in the installed app, so Vite builds with relative paths (`base: './'`).

|---|---|
| `src/ui/layout/` | The frame: `WorkspaceLayout.tsx` (`WorkspaceShell`, `ExplorerPanel`, `MainScreen` with its action bar, `DetailsPanel`, `ResizeHandle`), `usePanels.ts` (open / collapsed, widths, dragging), `panelWidth.ts` (the width rules, tested), `Layout.css` |

The frame is three columns, each a rounded card (`--card-radius`) on the darker frame colour (`--frame`), a gap (`--frame-gap`, the same number as `FRAME_GAP` in `panelWidth.ts`) apart and from the window's edge. Corners are concentric: a bar button in a card's corner sits `--bar-inset` from the card's edge, and `--bar-radius` is derived (`--card-radius` − 1px border − `--bar-inset`), so changing the card's radius or the inset keeps the buttons fitting; the collapsed panel is `COLLAPSED_WIDTH` = button + 2 × inset + borders. **Left**: the explorer, its header the tabs of the screens (Project, Code, Devices) and the collapse button; collapsed it is a column of the tab icons. **Centre**: the screen's action bar (undo, redo, the theme) over the screen. Code and Devices have two screens each, switched by the first button of the bar (it shows the screen it switches to: the flow icon the canvas, the sliders the details) and remembered per view: the details (lists and forms: Code the variables and blocks, Devices the devices, their pins and commands) and the canvas (Code the blocks and their flow, Devices the board and what is connected to it). **Right**: the details panel, open only while it has something to show (the connection panel, in Devices the selected device's test panel, in Code the selected block's details, else the selected variable's) and collapsed otherwise; open, its header is the collapse button on the left and the toolbar (Play, the eye, the bug, Stop, the Console's tab, the connection) in the right corner (Play is green while it can be pressed, Stop red while the program runs, the safe stop in the corner while it runs; see below); the Console's tab is the screen's icon with a red dot that blinks while an error is not read (it opens the Console view and the left panel); collapsed, the connection button sits in the header row and Run, Stop and the Console's tab are a column under it, and at its foot, while connected, the Live power display (`power/`); open, the same display is a row at the top of the panel. **Play, Stop and the safe stop** (`useVm.ts`). While connected the app asks `VM STATUS` every second (VM_CORE.MD "Remote": the run mode, whether a program is loaded and complete, the fault latch, the passes); the mode is named from `vm_run_mode_e` in the published enums. Play loads the project's program into the board and starts it, the eye and the bug do it with a live view or a debug (**Run, Live view and Debug**, below); Stop is `EXEC pause`, and Play on a paused program that is the one loaded, in the same mode, is `EXEC resume`. Play is green when connected and not running (or while the program running has changed since it was loaded), Stop red while running. While the program runs, the corner of the toolbar (where the connection button is) is the **safe stop**, a red button with a thin light line inside its edge that really sends `SYS STOP`: the board's safe state, the VM stopped and every device output switched off and suspended; the connection button sits beside it (in the collapsed column, on top of Play and Stop). A refusal is shown as a line in the action bar. **The safe state** (`SafeState.tsx`): `useVm` also asks `SYS SAFE_GET` every second; while the board is in its safe state the right panel's edge blinks red, the open panel's top says why (the reason's alias and description from `sys_safe_reason_e`: Stop, Deadman, Link lost, Power fault) and for how long, with **Resume** (`leaveSafeState`: the devices resumed, the ready program started again) and, while a device fault is latched, **Acknowledge the fault** (`EXEC ackFault`) first; collapsed, a red shield at the top of the column opens the panel. A firmware without SAFE_GET shows none. The connection button's colour is the link's state (`status-ok`, `status-warn`, `status-lost`) and opens the connection panel: **My board** and its name, Connect (in the link's colour and with its icon while connecting, reconnecting or connected) (with no chooser when the browser still allows the remembered board, else the chooser; the desktop app's own list below), the board has no battery clock, so the app gives it the time (`SYS TIME_SET`, UTC) each time the link comes up (`useConsole.ts`, which then reads the clock back and the board's error history; a firmware without them refuses, nothing is lost), Disconnect (red-outlined while there is a link to drop; it says `SYS BYE` first, as Forget does and a closing window as far as the page still can: the board turns a dead-man off and goes on with its program, a link that drops without it is a lost link as before), **Connect automatically** (the remembered board once per page load; the browser needs the two flags of BACKEND.md "The connection", and the panel says so when they are off) and Forget device (the link, the browser's permission and the remembered board dropped). Both panels are resized by a grip in the gap beside them (three dots, a sibling of the cards in `App.tsx` so their rounded clip does not cut it), dragged or moved with the arrow keys; their widths are remembered and the centre keeps its minimum. The Project view, the details screen of Devices and both screens of Code are written ("The project", "The Devices view", "The Code view" above); the canvas of Devices shows what it will hold.

`src/ui/` has no dependency on the backend or the engine; `src/app/` composes them with it. Aliases: `@ui/*` is `src/ui/*` (`tsconfig.json`, `vite.config.ts`, `vitest.config.ts`). The page's own font and button styles are in `Layout.css`; there is no CSS framework. Every bar of the frame takes its button and icon size from the tokens at the top of `Layout.css` (`--bar-button`, `--bar-icon`, `--bar-stroke`, `--bar-radius`). The shell's plain button and icon rules are inside `:where()` (no weight), so a component's own class always wins and a part looks in the app as on the kit page.

## Run, Live view and Debug

`src/app/run/`, `useVm.ts`: three buttons of the right toolbar start the program.

| Button | What it does |
|---|---|
| Play | **Run**: compiles the project's program (refused with the first mistake in the bar while it has any, or is empty), `loadProgram`, `leaveSafeState` with `EXEC normal`. Nothing is read back. |
| Eye | **Live view**: the same, compiled with `allEnableOuts`, and `SUBSCRIBE` to the plan of `engine.watch(result, 'flow')` first: each block's When done and every variable. A block lights while it acts, its wires with it, and a variable shows the value the board holds. |
| Bug | **Debug**: opens the Debug panel in the right panel (as the connection button opens the connection panel; one covers the other). **Start debugging** loads the program with `engine.watch(result, 'full')`: the value of every block output on its pin too. The panel holds **Stepping** (the VM's run modes: Continuous = `EXEC normal`, Loop by loop = `EXEC scan` and **Next loop** = `EXEC once`, Step by step = `EXEC block` and **Next block** = `EXEC next`; **Rewind** = `EXEC restart`; in step by step the board sends what each block changed at once (firmware: the telemetry sample at every stop in block mode), and `VM STATUS` `next_block` names the block the next **Next block** runs, which the canvas outlines dashed (`is-next`, `LiveView.next`)), **Time per step** (ms, `runit.run.stepMs`, 100 by default: the program's own clock stands still between requests, so Every, Timer and Periodic would never fire while stepping; each pass asked for moves it by this much, `VM SPEED` `step_ms`, 0 stands time still), **Slow motion** (`VM SPEED` `factor`: off, ×2, ×5, ×10, ×20) and **Keep a pulse lit for (ms)**. With the program started, a change of stepping or of slow motion acts on it at once; the step modes read from `VM STATUS` (`VM_RUN_SCAN`, `VM_RUN_BLOCK`) count as started (Stop pauses them). After a requested pass the board is `VM_RUN_FROZEN` with the scan mode still selected, which says nothing of a pause: `useVm` remembers the stepping it selected (`selected`) and takes a frozen program in a step mode as the started one, waiting for the next request. |

The board sends a value when it changes and a block's When done as a flag that is true on the passes it acted, and a pass lasts milliseconds, so every cell remembers when it was last true or changed and stays lit for the hold time (`runit.run.holdMs`, 500 by default; the stepping and the slow motion are remembered as `runit.run.stepping`, `runit.run.slow`). A program is loaded again by every start, but Play on a paused program that is the loaded one is only Resume (a paused debug stays a debug), and so is the eye or the bug in the same mode and slow motion; Rewind of a program that runs on its own goes on running from the start (the board freezes there, the app resumes it); the program of the project changing while it runs makes Play available again (`stale`) to load the new one. The telemetry stream is read in `useVm` (`link.on('telemetry')` into `LiveValues`, `run/live.ts`, redrawn at most every 60 ms and again when the oldest pulse expires); the screens read it from `LiveContext` (`useLive()`: `active` for a flag, `changed` for a value, `text`), which is empty unless a Live or Debug program is on the board and the link is up. The subscription is sent again when the link comes back. Cells are named by the engine's `variableKey`, `outputKey` and `doneKey`; `tests/app/live.test.ts`, `tests/engine/compiler/watch.test.ts`.

| File | What |
|---|---|
| `run/live.ts` | `RunMode`; `LiveValues` (pure: the cells, the hold time, `active` / `changed` / `nextExpiry`; a long value arrives in parts and is put together; a folder's child ids are ignored); `liveText`; `LiveContext`, `useLive`. |
| `run/DebugPanel.tsx`, `DebugPanel.css`, `useRunSettings.ts` | The Debug panel (start, stepping and its Next / Rewind, slow motion, hold time; why Start is not available, how far a load is) and the remembered settings. |
| `canvas/CanvasBlockView.tsx`, `CanvasWires.tsx` | A block lit while it acts (`is-pulse`), the value on an output pin (`canvas-pin-live`), the wires lit (`is-live`). A boolean the board holds colours the lead of its pin and its wire (green true, red false: `LiveView.flag`, held for the hold time after it was true, since a router such as Switch or If drives a branch true for one pass and clears it on the next). |
| `VariablesExplorer.tsx`, `VariableScreen.tsx` | A value variable's current value as a badge (`live-value`). |

## The Console

`src/app/console/`: what the board says on its own, read only (no commands go from it).

| File | What |
|---|---|
| `useConsole.ts` | `useConsole(link, state, interpreter)`: an `ErrorLog` on the errors stream (the same error again counts up, an answer and its copy on the stream are one; BACKEND.md "Errors for a user"), the logs stream as lines (`parseLogLine`: ESP_LOG's `I (854) tag: text` cut into level, uptime, tag, text; 1000 kept) and the link's changes as the app's own lines. An entry is read again at each render with the devices' interpreter (`useDevices().interpreter`), so it names devices and pins as they are now. `ConsoleContext` / `useErrors()` give any screen the errors and `ConsoleJumps` (where a reference leads: a device or its pin in Devices, a settings tab or the Project tab in Project, by the router key of the command; built in `App.tsx`). The board keeps the latest error records in RAM (`LOG ERRORS`, read each time the link comes up: an error of the start, one while no client was there), and `useConsole` dates what it shows by the board's clock: an error by the time in its record, a log line by its uptime plus the board's clock minus its uptime (`SYS TIME_GET`). |
| `ErrorView.tsx` | `ErrorView`: one entry as `ErrorEntry` with the app's names, the hint, the context steps, the pills of what it is about (a pin in place of its device, a device in place of a settings tab), Mark read and Remove. `ErrorsCard about=…`: the errors about a `refKey` (or several) as a card, shown only while there are some: on a device's screen (`device:<id>`, its pins' too), a pin's panel (`device:<id>/pin:<n>`), a settings tab (`router_key:<key>`) and the Project tab (the stored project's key: what the autostart refused); `ErrorsCard match=…`: the errors whose app target `match` takes (a variable's details). |
| `ConsoleScreen.tsx` | `ConsoleExplorer` (left): Everything, then each thing the errors are about (`subjectOf`: the first device, else a settings tab, else the board) with its unread count; a choice shows only those. `ConsoleScreen` (centre): All / Errors / Logs (`runit.console.show`), Mark read, Clear, the feed in arrival order, newest at the bottom (followed while scrolled to the end). All leaves out the board's error trace lines (`err_log.c`, `trace_errors`): the entry shows that chain read; Logs keeps them. |

Unread errors also mark what they are about where it is listed: a device row in Devices (red, with the count), a pin row of its Pins card, a settings tab in Project, a variable's row and entry in Code.
