# runit-app

The runIT app, written from scratch. So far: the VM engine in `src/engine/` (read `src/engine/ENGINE.md` first) the link to the board in `src/backend/` (`src/backend/BACKEND.md`), the UI kit in `src/ui/` and `design/`, and the app in `src/app/` (its frame, the connection, Run and Stop, the open project, the Project screen, the Devices view and its canvas (the board and the parts wired to it, the part creator), the Code view (variables, blocks and their canvas), Run with its live view and the Console), in a browser or as the desktop app in `electron/` (below).

## Rules

- **Facts come from the firmware.** The C in `runit-esp/components/vm/` is the truth; `generated/` (in this folder; the bundle `templates/generate_bundle.py` copies from `runit-esp/components/`) is what the app reads. Never a number or layout you cannot point to in C or in a descriptor: put the source in a comment, and a test that reads the C where it can.
- **The backend has no UI** and takes every number of the link from `generated/common/` and every command from the descriptors in `generated/services`, `generated/contracts` and `generated/devices` (`src/backend/definitions.ts` is the only file that reads `generated/`). No service, contract, command or field is named in its code: a new descriptor works with nothing to edit. The engine does not depend on it.
- **The engine has no UI, no DOM, no connection.** It is data in, data out, with its dependencies pointing down `wire` → `catalog` → `model` → `graph` → `expression` → `compiler` → `recover`. The only file that reads `generated/` is `src/engine/generated/index.ts`.
- **A mistake in a project is a diagnostic, not an exception.**
- Aliases: `@engine/*` is `src/engine/*`, `@generated/*` is `generated/*`, `@library/*` is `../library/*` (the hardware library, [library/LIBRARY.md](../library/LIBRARY.md)) (see `tsconfig.json`, `vite.config.ts`, `vitest.config.ts`).

## The app's frame

`npm run dev` serves the app at `http://localhost:5180` (a fixed port; localhost is a secure context, so Web Bluetooth works; Chrome or Edge). `npm run build` typechecks and builds it. **A devkit board** (firmware built with `CONFIG_RUNIT_BOARD_DEVKIT`): `npm run dev:devkit` (port 5181) or `npm run app:devkit`. It is the same app with `VITE_RUNIT_BOARD=devkit` (`.env.devkit`), so `bundledBoard()` gives `board_devkit.json`: only the ESP pins as device 0, no chips, no power rails or monitor. The window title says `runIT (devkit)`. A hot reload of `App.tsx` or of a backend file makes `useLink` a new link that is not connected while the screen still shows the old state (commands fail "not connected"): reload the page. Vite caches the imported `generated/` descriptors: after `templates/sync.sh` changes them, `touch` the changed JSON files (or restart `npm run dev`) and reload. The desktop app takes Chromium switches after `--`: `npm run app -- --remote-debugging-port=9345` lets a script drive it over the DevTools protocol.

The parts come from the hardware library (`_SOFTWARE/library/parts/`, [library/LIBRARY.md](../library/LIBRARY.md)); the app hard-codes only the standard connectors it draws. What the wires decide goes into the project's devices and start commands, where the details screen shows it.

## The desktop app

The same page in Electron's Chromium, so the board is found and opened again with no browser flags and no chooser. `npm run app` opens it on the Vite dev server (hot reload; an `npm run dev` already running is reused), `npm run app:start` on the built page, `npm run app:dist` builds the Windows installer into `release/` (`electron-builder.yml`). One instance runs per profile (a second launch brings the window forward: two instances on one profile would lose the page's storage); the dev app has its own profile (`<userData>-dev`), so it runs beside the installed one and remembers its own board. Both launchers go through `electron/start.mjs`, which drops `ELECTRON_RUN_AS_NODE` (a terminal in VS Code sets it, and Electron would start as plain Node). Where Windows refuses to rename folders under `Documents` (Controlled folder access) the build fails with `EPERM … rename win-unpacked.tmp`: build into another folder, `npm run app:dist -- -c.directories.output=<path>`.

A block lights while it acts, its wires with it, a variable shows the value the board holds, and an output pin its value. |
| Bug | **Debug**: opens the Debug panel in the right panel (as the connection button opens the connection panel; one covers the other). **Start debugging** loads the program with `engine.watch(result, 'full')` (the same plan as the live view). The panel holds **Stepping** (the VM's run modes: Continuous = `EXEC normal`, Loop by loop = `EXEC scan` and **Next loop** = `EXEC once`, Step by step = `EXEC block` and **Next block** = `EXEC next`; **Rewind** = `EXEC restart`; in step by step the board sends what each block changed at once (firmware: the telemetry sample at every stop in block mode), and `VM STATUS` `next_block` names the block the next **Next block** runs, which the canvas outlines dashed (`is-next`, `LiveView.next`)), **Time per step** (ms, `runit.run.stepMs`, 100 by default: the program's own clock stands still between requests, so Every, Timer and Periodic would never fire while stepping; each pass asked for moves it by this much, `VM SPEED` `step_ms`, 0 stands time still), **Slow motion** (`VM SPEED` `factor`: off, ×2, ×5, ×10, ×20) and **Keep a pulse lit for (ms)**. With the program started, a change of stepping or of slow motion acts on it at once; the step modes read from `VM STATUS` (`VM_RUN_SCAN`, `VM_RUN_BLOCK`) count as started (Stop pauses them). After a requested pass the board is `VM_RUN_FROZEN` with the scan mode still selected, which says nothing of a pause: `useVm` remembers the stepping it selected (`selected`) and takes a frozen program in a step mode as the started one, waiting for the next request. |

The board sends a value when it changes and a block's When done as a flag that is true on the passes it acted, and a pass lasts milliseconds, so every cell remembers when it was last true or changed and stays lit for the hold time (`runit.run.holdMs`, 500 by default; the stepping and the slow motion are remembered as `runit.run.stepping`, `runit.run.slow`). A program is loaded again by every start, but Play on a paused program that is the loaded one is only Resume (a paused debug stays a debug), and so is the eye or the bug in the same mode and slow motion; Rewind of a program that runs on its own goes on running from the start (the board freezes there, the app resumes it); the program of the project changing while it runs makes Play available again (`stale`) to load the new one. The telemetry stream is read in `useVm` (`link.on('telemetry')` into `LiveValues`, `run/live.ts`, redrawn at most every 60 ms and again when the oldest pulse expires); the screens read it from `LiveContext` (`useLive()`: `active` for a flag, `changed` for a value, `text`), which is empty unless a Live or Debug program is on the board and the link is up. The subscription is sent again when the link comes back. Cells are named by the engine's `variableKey`, `outputKey` and `doneKey`; `tests/app/live.test.ts`, `tests/engine/compiler/watch.test.ts`.

| File | What |
|---|---|
| `run/live.ts` | `RunMode`; `LiveValues` (pure: the cells, the hold time, `active` / `changed` / `nextExpiry`; a long value arrives in parts and is put together; a folder's child ids are ignored); `liveText`; `LiveContext`, `useLive`. |
| `run/DebugPanel.tsx`, `DebugPanel.css`, `useRunSettings.ts` | The Debug panel (start, stepping and its Next / Rewind, slow motion, hold time; why Start is not available, how far a load is) and the remembered settings. |
| `canvas/CanvasBlockView.tsx`, `CanvasWires.tsx` | A block lit while it acts (`is-pulse`), the value on an output pin (`canvas-pin-live`), the wires lit (`is-live`). A boolean the board holds colours the lead of its pin and its wire (green true, red false: `LiveView.flag`, held for the hold time after it was true, since a router such as Switch or If drives a branch true for one pass and clears it on the next). |
| `VariablesExplorer.tsx`, `VariableScreen.tsx` | A value variable's current value as a badge (`live-value`). |

## The Console

`src/app/console/`: what the board says on its own, read only (no commands go from it).

| File | What |
|---|---|
| `useConsole.ts` | `useConsole(link, state, interpreter)`: an `ErrorLog` on the errors stream (the same error again counts up, an answer and its copy on the stream are one; BACKEND.md "Errors for a user"), the logs stream as lines (`parseLogLine`: ESP_LOG's `I (854) tag: text` cut into level, uptime, tag, text; 1000 kept) and the link's changes as the app's own lines. An entry is read again at each render with the devices' interpreter (`useDevices().interpreter`), so it names devices and pins as they are now. `ConsoleContext` / `useErrors()` give any screen the errors and `ConsoleJumps` (where a reference leads: a device or its pin in Devices, a settings tab or the Project tab in Project, by the router key of the command; built in `App.tsx`). The board keeps the latest error records in RAM (`LOG ERRORS`, read each time the link comes up: an error of the start, one while no client was there), and `useConsole` dates what it shows by the board's clock: an error by the time in its record, a log line by its uptime plus the board's clock minus its uptime (the `SYS TIME` read, then `SYS PING`'s uptime, the app's time between the two answers added to the clock). |
| `ErrorView.tsx` | `ErrorView`: one entry as `ErrorEntry` with the app's names, the hint, the context steps, the pills of what it is about (a pin in place of its device, a device in place of a settings tab), Mark read and Remove. `ErrorsCard about=…`: the errors about a `refKey` (or several) as a card, shown only while there are some: on a device's screen (`device:<id>`, its pins' too), a pin's panel (`device:<id>/pin:<n>`), a settings tab (`router_key:<key>`) and the Project tab (the stored project's key: what its load at a boot refused); `ErrorsCard match=…`: the errors whose app target `match` takes (a variable's details). |
| `ConsoleScreen.tsx` | `ConsoleExplorer` (left): Everything, then each thing the errors are about (`subjectOf`: the first device, else a settings tab, else the board) with its unread count; a choice shows only those. `ConsoleScreen` (centre): All / Errors / Logs (`runit.console.show`), Mark read, Clear, the feed in arrival order, newest at the bottom (followed while scrolled to the end). All leaves out the board's error trace lines (`err_log.c`, `trace_errors`): the entry shows that chain read; Logs keeps them. |

Unread errors also mark what they are about where it is listed: a device row in Devices (red, with the count), a pin row of its Pins card, a settings tab in Project, a variable's row and entry in Code.

## UI kit

`src/ui/` holds the shared UI parts: `styles/` the theme, status and error tokens, `components/<Name>/` one folder per part, its React component next to its CSS, all exported from `@ui/components` (`src/ui/components/index.ts`).

| Part | For |
|---|---|
| `Button`, `ToggleChip` | every text button (variants default, primary, danger, dashed; `block` fills the row); a pill that toggles. Icon-only buttons of the bars stay the shell's plain `<button>` |
| `TextField`, `NumberField`, `EditableField`, `InlineRename` | text and numbers: a plain field, a number committed only when valid (empty while not set), a field with the pencil / lock, a rename in place |
| `ListableField`, `ChoiceField` | the one dropdown (the app draws the list: groups, hints, badges, opens upwards when needed); a choice among things with an empty option and a stored value no longer offered |
| `Switch`, `SegmentedSwitch`, `Slider` | on / off; one of a few; a number on a scale (applied when the thumb is let go, the value beside it) |
| `FormRow`, `FormGrid`, `FieldLabel`, `FieldError`, `Card`, `CardStack`, `PanelHeader` | a labelled control with its hint (its `note` is the help text, shown in help mode), two columns, what is wrong with a value, a titled group (`actions` at the right of its title, `help` its text in help mode), the title row of a details panel |
| `TreeSlab`, `TreeDisclosure`, `TreeAction`, `TreeChildren` | a row of a list or a tree (lead, name, badges, a reference pill, the delete action, selected / error / search / drag states, `refKey`), a folder's chevron and rows |
| `Badge`, `TypeBadge`, `TypeLead`, `DeviceTile`, `RefPill` | a tag; an element type (`f32`); a variable's lead square (a boolean's shows its value); a device's square (icon by its tags); a pill that names another thing and jumps to it |
| `OptionMenu`, `MenuOption`, `PaletteSearch`, `PaletteSectionHeader` | a list of choices; a palette's search (`matchesSearch`, `bestMatch`) and section heading |
| `ErrorEntry`, `LogLine` | one error as a user reads it (severity, message, hint, where, the pills of what it is about, the chain behind a disclosure, unread edge, count, time, actions; `severityTone`); one console line (time, level letter coloured, tag, text; `app` for the app's own) |
| `HelpOverlay` | help mode (the toolbar's Help button, `.help-toggle`): an outline over each element of the shell that has help: a `data-help` text, else a button's title (the overlay's own boxes are left out; a control inside a `data-help` element is explained by that element). A click on an outline shows the text beside it (a click elsewhere or Escape hides it), and the screen takes no other click meanwhile. `FormRow` sets `data-help` from its note; a toolbar button sets it itself where it has no title |

**A screen builds from these parts, never from the raw markup they draw** (`<input>`, `<select>`, `className="badge …"`, a text `<button>`). `tools/check-ui.mjs` holds every `.tsx` outside `src/ui/components` to that: `npm run check:ui`, `tests/ui/check-ui.test.ts` (part of `npm test`), and a Claude Code hook (`.claude/settings.json`, PostToolUse on Edit / Write) that hands the findings of an edited file back to the agent. A line that must stay raw says why with a `ui-raw: <reason>` comment on it or on the line above. A part that is missing is added here (component, CSS, the kit page) before a screen uses it.

`design/ui-kit.html` is the kit as one page, open it in a browser. It shows each part on the data the backend has, never on typed-in examples:

| On the page | Comes from |
|---|---|
| Variables: the six element types, array / retained / protected / constant, folders, references, the name limit, what the engine refuses | `@engine` `Variable`, `VALUE_TYPES`, `NAME_MAX`, `checkVariables` |
| Devices: the catalog (label, tags, contracts, config fields, pin labels and modes), the project's devices with an id, a name, system and suspended | `bundledServiceCatalog()` and `generated/devices` |
| Blocks: instances and their input / enable / output pins | the compile result and `bundledBlockTypes()` |
| Errors: message, where, the chain, what each ref points at (device, pin, block pin, variable) | records captured from a board (`design/board-errors.json`, by `tests/hardware/kit-capture.hw.test.ts`; `tests/backend/errors.test.ts` holds them to the current record format) read by `ErrorInterpreter` with `programRefs` and `deviceRefs` |
| Link, dead-man, safe state | `LinkState`, `DeadMan`, `leaveSafeState` (BACKEND.md) |

`npm run kit` rebuilds `design/kit-data.js` from those (`design/build-kit.mjs`; the sample project is `design/sample.ts`). The captured records are made again from a board with `KIT_CAPTURE=1 npm run test:hw` (`tests/hardware/kit-capture.hw.test.ts`). A part's tile carries the key of what it shows (`device:1/pin:22`, `block:e/input:1`, `variable:x`), the same key an error's ref has (`refKey`): that is how an error marks the tiles it is about.

What a UI shows follows from the backend: names, never ids; a block's enable pin is **Run when** and its enable output **When done**; a pin is always `#n`, followed by the user's alias when it has one (`#22 LED blue`); the descriptor's own name (`P26`, `CH3`) is only a tooltip.
