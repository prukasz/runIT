# runit-app

The runIT app, written from scratch. So far: the VM engine in `src/engine/` (read `src/engine/ENGINE.md` first) the link to the board in `src/backend/` (`src/backend/BACKEND.md`), the UI kit in `src/ui/` and `design/`, and the app in `src/app/` (its frame, the connection, Run and Stop, the open project, the Project screen, the Devices view, the variables of the Code view and the Console), in a browser or as the desktop app in `electron/` (below).

## Rules

- **Facts come from the firmware.** The C in `components/vm/` is the truth; `generated/` (the bundle `templates/generate_bundle.py` copies from `components/`) is what the app reads. Never a number or layout you cannot point to in C or in a descriptor: put the source in a comment, and a test that reads the C where it can.
- **The backend has no UI** and takes every number of the link from `generated/common/` and every command from the descriptors in `generated/services`, `generated/contracts` and `generated/devices` (`src/backend/definitions.ts` is the only file that reads `generated/`). No service, contract, command or field is named in its code: a new descriptor works with nothing to edit. The engine does not depend on it.
- **The engine has no UI, no DOM, no connection.** It is data in, data out, with its dependencies pointing down `wire` → `catalog` → `model` → `graph` → `expression` → `compiler` → `recover`. The only file that reads `generated/` is `src/engine/generated/index.ts`.
- **A mistake in a project is a diagnostic, not an exception.**
- Aliases: `@engine/*` is `src/engine/*`, `@generated/*` is `../generated/*` (see `tsconfig.json`, `vitest.config.ts`).

## The app's frame

`npm run dev` serves the app at `http://localhost:5180` (a fixed port; localhost is a secure context, so Web Bluetooth works; Chrome or Edge). `npm run build` typechecks and builds it. A hot reload of `App.tsx` or of a backend file makes `useLink` a new link that is not connected while the screen still shows the old state (commands fail "not connected"): reload the page. Vite caches the imported `generated/` descriptors: after `templates/sync.sh` changes them, `touch` the changed JSON files (or restart `npm run dev`) and reload. The desktop app takes Chromium switches after `--`: `npm run app -- --remote-debugging-port=9345` lets a script drive it over the DevTools protocol.

## The project

`src/app/project/`: the open project and its screen.

| `useProject.ts` | The project for the screens: `edit(change, key?)` (edits with the same key less than 1.5 s apart, typing in one field, are one undo step), New, Open… (the file chooser), Save (a download; the desktop app asks where), Restore previous (New and Open keep the project they replace; a restore swaps it back). Tested in `tests/app/settings.test.ts`. |

## The desktop app

The same page in Electron's Chromium, so the board is found and opened again with no browser flags and no chooser. `npm run app` opens it on the Vite dev server (hot reload; an `npm run dev` already running is reused), `npm run app:start` on the built page, `npm run app:dist` builds the Windows installer into `release/` (`electron-builder.yml`). One instance runs per profile (a second launch brings the window forward: two instances on one profile would lose the page's storage); the dev app has its own profile (`<userData>-dev`), so it runs beside the installed one and remembers its own board. Both launchers go through `electron/start.mjs`, which drops `ELECTRON_RUN_AS_NODE` (a terminal in VS Code sets it, and Electron would start as plain Node). Where Windows refuses to rename folders under `Documents` (Controlled folder access) the build fails with `EPERM … rename win-unpacked.tmp`: build into another folder, `npm run app:dist -- -c.directories.output=<path>`.

| File | What |
|---|---|
| `electron/main.mjs` | The window (never throttled in the background: `backgroundThrottling: false` and the Chromium switches against background and occluded-window throttling, so the link's timers and the dead-man's heartbeat keep their pace behind another window) and the board chooser. Electron has none: `requestDevice()` fires `select-bluetooth-device` with every scan result until it is answered. The page names the board to pick when the scan sees it (`ble:want`), or gets the scan (`ble:devices`) and answers with the user's choice (`ble:select`, '' cancels). `ble:gesture` runs `globalThis.__runitGesture` with a user gesture (`executeJavaScript(…, true)`), so `requestDevice()` runs at start with no click. |
| `electron/preload.cjs` | `window.runitDesktop`, the page's side of those messages |
| `src/app/desktop.ts` | `desktop` (undefined in a browser) and `withGesture` |

The page tells the two apart only in `useLink.ts`: on the desktop it remembers the scan's id of the board (`scanId`, the address, which is not the page's `BluetoothDevice.id`), picks it when the scan sees it (gives up after 20 s with "not found nearby"), and with no board remembered the connection panel lists the boards nearby. With **Connect automatically** the app opens the board when it starts and after a reload. The page is loaded from a file in the installed app, so Vite builds with relative paths (`base: './'`).

| Where | What |
|---|---|
| `src/ui/layout/` | The frame: `WorkspaceLayout.tsx` (`WorkspaceShell`, `ExplorerPanel`, `MainScreen` with its action bar, `DetailsPanel`, `ResizeHandle`), `usePanels.ts` (open / collapsed, widths, dragging), `panelWidth.ts` (the width rules, tested), `Layout.css` |
| `src/ui/hooks/` | `useStorage.ts`: remembered choices and flags, every read and write guarded |
| `src/app/` | The app: `App.tsx` composes the frame, `useLink.ts` holds the link's state for the screens and which board is the user's, `useVm.ts` Run and Stop, `ConnectionPanel.tsx`, `project/` the open project (below) |

The frame is three columns, each a rounded card (`--card-radius`) on the darker frame colour (`--frame`), a gap (`--frame-gap`, the same number as `FRAME_GAP` in `panelWidth.ts`) apart and from the window's edge. Corners are concentric: a bar button in a card's corner sits `--bar-inset` from the card's edge, and `--bar-radius` is derived (`--card-radius` − 1px border − `--bar-inset`), so changing the card's radius or the inset keeps the buttons fitting; the collapsed panel is `COLLAPSED_WIDTH` = button + 2 × inset + borders. **Left**: the explorer, its header the tabs of the screens (Project, Code, Devices) and the collapse button; collapsed it is a column of the tab icons. **Centre**: the screen's action bar (undo, redo, the theme) over the screen. Code and Devices have two screens each, switched by the first button of the bar (it shows the screen it switches to: the flow icon the canvas, the sliders the details) and remembered per view: the details (lists and forms: Code the variables and blocks, Devices the devices, their pins and commands) and the canvas (Code the blocks and their flow, Devices the board and what is connected to it). **Right**: the details panel, open only while it has something to show (the connection panel, in Devices the selected device's test panel, in Code the selected variable's details) and collapsed otherwise; open, its header is the collapse button on the left and the toolbar (Run, Stop, the Console's tab, the connection) in the right corner (Run is green while it can be pressed, Stop red while the program runs, the safe stop in the corner while it runs; see below); the Console's tab is the screen's icon with a red dot that blinks while an error is not read (it opens the Console view and the left panel); collapsed, the connection button sits in the header row and Run, Stop and the Console's tab are a column under it. **Run, Stop and the safe stop** (`useVm.ts`). While connected the app asks `VM STATUS` every second (VM_CORE.MD "Remote": the run mode, whether a program is loaded and complete, the fault latch, the passes); the mode is named from `vm_run_mode_e` in the published enums. With a ready program on the board, Run and Stop are real: Run is `leaveSafeState` with `EXEC normal` (so it also leaves a safe stop), or `EXEC resume` from a pause; Stop is `EXEC pause`. With no program on the board, or a firmware without STATUS, they are a simulation that sends nothing (their titles say which). Run is green when connected and not running, Stop red while running. While the program runs, the corner of the toolbar (where the connection button is) is the **safe stop**, a red button with a thin light line inside its edge that really sends `SYS STOP`: the board's safe state, the VM stopped and every device output switched off and suspended; the connection button sits beside it (in the collapsed column, on top of Run and Stop). A refusal is shown as a line in the action bar. The connection button's colour is the link's state (`status-ok`, `status-warn`, `status-lost`) and opens the connection panel: **My board** and its name, Connect (in the link's colour and with its icon while connecting, reconnecting or connected) (with no chooser when the browser still allows the remembered board, else the chooser; the desktop app's own list below), the board has no battery clock, so the app gives it the time (`SYS TIME_SET`, UTC) each time the link comes up (`useConsole.ts`, which then reads the clock back and the board's error history; a firmware without them refuses, nothing is lost), Disconnect (red-outlined while there is a link to drop; it says `SYS BYE` first, as Forget does and a closing window as far as the page still can: the board turns a dead-man off and goes on with its program, a link that drops without it is a lost link as before), **Connect automatically** (the remembered board once per page load; the browser needs the two flags of BACKEND.md "The connection", and the panel says so when they are off) and Forget device (the link, the browser's permission and the remembered board dropped). Both panels are resized by a grip in the gap beside them (three dots, a sibling of the cards in `App.tsx` so their rounded clip does not cut it), dragged or moved with the arrow keys; their widths are remembered and the centre keeps its minimum. The Project view, the details screen of Devices and the variables of Code are written ("The project", "The Devices view", "The Code view" above); the two canvases show what they will hold.

`src/ui/` has no dependency on the backend or the engine; `src/app/` composes them with it. Aliases: `@ui/*` is `src/ui/*` (`tsconfig.json`, `vite.config.ts`, `vitest.config.ts`). The page's own font and button styles are in `Layout.css`; there is no CSS framework. Every bar of the frame takes its button and icon size from the tokens at the top of `Layout.css` (`--bar-button`, `--bar-icon`, `--bar-stroke`, `--bar-radius`). The shell's plain button and icon rules are inside `:where()` (no weight), so a component's own class always wins and a part looks in the app as on the kit page.

## The Console

`src/app/console/`: what the board says on its own, read only (no commands go from it).

| File | What |
|---|---|
| `useConsole.ts` | `useConsole(link, state, interpreter)`: an `ErrorLog` on the errors stream (the same error again counts up, an answer and its copy on the stream are one; BACKEND.md "Errors for a user"), the logs stream as lines (`parseLogLine`: ESP_LOG's `I (854) tag: text` cut into level, uptime, tag, text; 1000 kept) and the link's changes as the app's own lines. An entry is read again at each render with the devices' interpreter (`useDevices().interpreter`), so it names devices and pins as they are now. `ConsoleContext` / `useErrors()` give any screen the errors and `ConsoleJumps` (where a reference leads: a device or its pin in Devices, a settings tab or the Project tab in Project, by the router key of the command; built in `App.tsx`). The board keeps the latest error records in RAM (`LOG ERRORS`, read each time the link comes up: an error of the start, one while no client was there), and `useConsole` dates what it shows by the board's clock: an error by the time in its record, a log line by its uptime plus the board's clock minus its uptime (`SYS TIME_GET`). |
| `ErrorView.tsx` | `ErrorView`: one entry as `ErrorEntry` with the app's names, the hint, the context steps, the pills of what it is about (a pin in place of its device, a device in place of a settings tab), Mark read and Remove. `ErrorsCard about=…`: the errors about a `refKey` (or several) as a card, shown only while there are some: on a device's screen (`device:<id>`, its pins' too), a pin's panel (`device:<id>/pin:<n>`), a settings tab (`router_key:<key>`) and the Project tab (the stored project's key: what the autostart refused); `ErrorsCard match=…`: the errors whose app target `match` takes (a variable's details). |
| `ConsoleScreen.tsx` | `ConsoleExplorer` (left): Everything, then each thing the errors are about (`subjectOf`: the first device, else a settings tab, else the board) with its unread count; a choice shows only those. `ConsoleScreen` (centre): All / Errors / Logs (`runit.console.show`), Mark read, Clear, the feed in arrival order, newest at the bottom (followed while scrolled to the end). All leaves out the board's error trace lines (`err_log.c`, `trace_errors`): the entry shows that chain read; Logs keeps them. |

Unread errors also mark what they are about where it is listed: a device row in Devices (red, with the count), a pin row of its Pins card, a settings tab in Project, a variable's row and entry in Code.

## UI kit

`src/ui/` holds the shared UI parts: `styles/` the theme, status and error tokens, `components/<Name>/` one folder per part, its React component next to its CSS, all exported from `@ui/components` (`src/ui/components/index.ts`).

| Part | For |
|---|---|
| `Button`, `ToggleChip` | every text button (variants default, primary, danger, dashed; `block` fills the row); a pill that toggles. Icon-only buttons of the bars stay the shell's plain `<button>` |
| `TextField`, `NumberField`, `EditableField`, `InlineRename` | text and numbers: a plain field, a number committed only when valid, a field with the pencil / lock, a rename in place |
| `ListableField`, `ChoiceField` | the one dropdown (the app draws the list: groups, hints, badges, opens upwards when needed); a choice among things with an empty option and a stored value no longer offered |
| `Switch`, `SegmentedSwitch` | on / off; one of a few |
| `FormRow`, `FormGrid`, `FieldLabel`, `FieldError`, `Card`, `CardStack`, `PanelHeader` | a labelled control with its hint (its `note` is the help text, shown in help mode), two columns, what is wrong with a value, a titled group (`actions` at the right of its title, `help` its text in help mode), the title row of a details panel |
| `TreeSlab`, `TreeDisclosure`, `TreeAction`, `TreeChildren` | a row of a list or a tree (lead, name, badges, a reference pill, the delete action, selected / error / search / drag states, `refKey`), a folder's chevron and rows |
| `Badge`, `TypeBadge`, `TypeLead`, `DeviceTile`, `RefPill` | a tag; an element type (`f32`); a variable's lead square (a boolean's shows its value); a device's square (icon by its tags); a pill that names another thing and jumps to it |
| `OptionMenu`, `MenuOption`, `PaletteSearch`, `PaletteSectionHeader` | a list of choices; a palette's search (`matchesSearch`, `bestMatch`) and section heading |
| `ErrorEntry`, `LogLine` | one error as a user reads it (severity, message, hint, where, the pills of what it is about, the chain behind a disclosure, unread edge, count, time, actions; `severityTone`); one console line (time, level letter coloured, tag, text; `app` for the app's own) |
| `HelpOverlay` | help mode (the toolbar's Help button, `.help-toggle`): an outline over each element of the shell that has help: a `data-help` text, else a button's title (the overlay's own boxes are left out; a control inside a `data-help` element is explained by that element). A click on an outline shows the text beside it (a click elsewhere or Escape hides it), and the screen takes no other click meanwhile. `FormRow` sets `data-help` from its note; a toolbar button sets it itself where it has no title |

**A screen builds from these parts, never from the raw markup they draw** (`<input>`, `<select>`, `className="badge …"`, a text `<button>`). `tools/check-ui.mjs` holds every `.tsx` outside `src/ui/components` to that: `npm run check:ui`, `tests/ui/check-ui.test.ts` (part of `npm test`), and a Claude Code hook (`.claude/settings.json`, PostToolUse on Edit / Write) that hands the findings of an edited file back to the agent. A line that must stay raw says why with a `ui-raw: <reason>` comment on it or on the line above. A part that is missing is added here (component, CSS, the kit page) before a screen uses it.

`design/ui-kit.html` is the kit as one page, open it in a browser. It shows each part on the data the backend has, never on typed-in examples:

| On the page | Comes from |
|---|---|
| Variables: the six element types, array / retained / protected / constant, folders, references, the name limit, what the engine refuses | `@engine` `Variable`, `VALUE_TYPES`, `NAME_MAX`, `checkVariables` |
| Devices: the catalog (label, tags, contracts, config fields, pin labels and modes), the project's devices with an id, a name, system and suspended | `bundledServiceCatalog()` and `generated/devices` |
| Blocks: instances and their input / enable / output pins | the compile result and `bundledBlockTypes()` |
| Errors: message, where, the chain, what each ref points at (device, pin, block pin, variable) | records captured from a board (`design/board-errors.json`) read by `ErrorInterpreter` with `programRefs` and `deviceRefs` |
| Link, dead-man, safe state | `LinkState`, `DeadMan`, `leaveSafeState` (BACKEND.md) |

`npm run kit` rebuilds `design/kit-data.js` from those (`design/build-kit.mjs`; the sample project is `design/sample.ts`). The captured records are made again from a board with `KIT_CAPTURE=1 npm run test:hw` (`tests/hardware/kit-capture.hw.test.ts`). A part's tile carries the key of what it shows (`device:1/pin:22`, `block:e/input:1`, `variable:x`), the same key an error's ref has (`refKey`): that is how an error marks the tiles it is about.

What a UI shows follows from the backend: names, never ids; a block's enable pin is **Run when** and its enable output **When done**; a pin is always `#n`, followed by the user's alias when it has one (`#22 LED blue`); the descriptor's own name (`P26`, `CH3`) is only a tooltip.
