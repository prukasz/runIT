**Accessors (`accessors.ts`, 2026-09-27):** a pin stores an `ObjectPath` (`project/document.ts`): a root project ID plus steps `index` / `name` / `dynamic` (position = another path, read live). The compiler:
- re-roots through fixed folder entries (`motor[1][2]` → `gains[2]`: cacheable on the device), keeping a trailing folder step (the slot, what CLONE writes into);
- turns names into positions where the folder is known, and keeps names only below a live cell (`liveCells`: folder entries a block re-links, CLONE) or a dynamic child;
- compiles each dynamic position to its own accessor with a lower wire ID (`REF` targets exist first) and checks the nesting against `CONFIG_VM_ACCESSOR_MAX_DEPTH`;
- shares one accessor between identical paths (`keys` lists the users), checks bounds, types and names statically (the firmware error each check mirrors is on the diagnostic), and sizes the arena.
Golden fixture: `compiler/fixtures/accessor-samples.json` (`accessorSamples.test.ts`), run on a board by `runit-esp/scripts/accessor_samples_test.py`.

**Blocks (`blocks.ts`, 2026-09-27):** `ProgramBlock` (`project/document.ts`): type key, `inputs` (paths, null = unwired), `outputs` (a user object it drives, or null), `enables`, `enableMode`, `onError`, `eno`, `settings` (state fields by name; enum members by name), `expression` (EXPR / EXPR_BIT: constants + RPN tokens), `body` (FOR: blocks after it in the loop). Block ID = list position.
- `planBlocks` (before objects): block-owned objects in section `blocks`, `<id>:q<n>` for every listed output pin and `<id>:eno`, so wires to them are plain paths; driven user objects (mutable, `upd_resetable`); accessor requests `block:<id>:in<n>` / `en<n>`; pin counts, required inputs, one writer per object.
- `encodeBlocks` (after): pin kinds against what the path reaches (value pins refuse folders, CLONE's cell must be a folder entry); state from the settings (ranges per C type, enum members, a 4-byte union typed by input 0, the FOR span with nesting checks); expression bytecode checked like the device (operands, stack, one result); the prose load rules of PERIODIC, ACTION, LATCH and the IO blocks (`TYPE_RULES`).
- Golden: every EXPR / EXPR_BIT descriptor example byte for byte (`blocks.test.ts`); `fixtures/program-samples.json` (`programSamples.test.ts`): 13 blocks of 12 types, run by `runit-esp/scripts/program_samples_test.py`.
- Block semantics to know when writing samples: EXPR runs only on a fresh input or a fresh enable (user objects set at load are not fresh; put a PERIODIC's ENO, its tick, on the block's EN); EDGE compares with the previous pass, so its threshold is a change within one pass.

**ID rule:** the project file stores stable string IDs only. The device has three dense wire ID spaces (objects, accessors, blocks, each 0..count-1); the compiler assigns them on every compile and returns the map back. The object space is a list of sections, numbered in order: the user's tree first, then block-owned objects (outputs, ENO; `upd_resetable` 1). References may cross sections; IDs must be unique across all of them.

**Firmware values come from `data-structures/`, never literals.** Board defaults (GATT profile with flags and buffer bytes, connector bindings per provider incl. `#if CONFIG_` ones, connector registry limits, per-connector frame cap) are published by `generate-streams.py` into `streams.generated.json` → `runitStreamCatalog().board`; VM per-packet record sizes and batch limits (`vmCatalog.wire`), `payload_size` range (`payloadMax`, `maxElements`) from vm-program / vm-model. Only Bluetooth SIG constants (ATT 512, standard services 0x1800/0x1801/0x180A) and C type ranges stay in code. After a firmware change: rerun the generators, then `npm test`.

**Stored formats:** the project JSON is the source of truth; upload bundles are derived (inspect, diff, replay) and never edited by hand. User devices have one editable `name`; older user entries in `deviceAliases` migrate into it on workspace load. Board display names use project `deviceAliases` keyed by `board:<id>`, edited as Name in Configuration. `withDeviceAliases` creates a display catalog for lists, commands and canvas pickers; IDs and firmware frames stay unchanged. Name edits use the device workspace's undo/autosave and project Open/Save.

**I2C installs:** Every install packet's `i2c_addr` has a nonempty `@one-of` list in its decoder header; the device generator enforces this. The app shows available addresses in hex, starts new devices at the first choice and flags loaded values outside the list. Install cards contain controls only; their wire-packet explanation is omitted.

**Install pin modes:** a pin on another device is a `pin_ref_wire_t` install field; its `@modes [...]` limits the mode to the purpose, `@default-mode` picks the start (ADS7128 ALERT: `$SYS_IO_MODE_INPUT_PULLUP`); install defaults read generated field defaults before the first choice. A pin provider must expose the mode through its device-specific `sys_io_set_mode` contract, so the picker intersects the install field choices with that provider's choices. A provider change adjusts an unsupported saved mode in the same undo step.

**Built-in pin defaults:** A device header's `//#property PIN-MODE` with `@default $SYMBOL` flows through `@arg PIN-MODE` to the set-mode contract. Use it only for a mode that firmware establishes without a setup command. ADS7128 starts all eight pins as ADC; the Default settings table shows ADC as the device default, while the project setup list stays empty until the user adds a setting.

**Header text in the app (2026-09-28):** pin groups are keyed by the `pin_ref_wire_t` field (`intr_pin`), the same key `board.generated.json` uses, so `InstallPinGroup.use` (the header's `@alias`, else `pinUseLabel`) also names the board devices' pins (`BoardPinLink.label`, "Pins it uses", pin users). Every `@note` (install field, pin group, contract parameter; parameter note falls back to its property's, then the generic field's) sits behind an (i) button next to the label: `components/FieldNote` (`FieldLabel`), closed until clicked. Device headers carry only tags the app reads (`device-annotations.md`).

**Device error importance:** Firmware uses importance as a severity threshold, preserving the original error level: Disabled ignores every error of the device, Critical included (the user's risk: `ErrorActionsField` shows `DISABLED_IMPORTANCE_WARNING`, `checkSetup` a project warning); a device starts at Low (the packet field's `@default`, so forms start there), which exposes only Critical actions; Medium exposes High + Critical, High exposes Medium through Critical, and Critical exposes all levels. The C enum descriptions flow through `data-structures/enums.json` and `contracts.generated.json` to the app hint; `reachableErrorLevels` controls action pickers and `clampErrorActions` clears inactive slots.

**Settings baseline:** the board can't report BLE / connector state, but after boot it runs its defaults + its stored code. `useBoardCode` reads the stored code's settings frames once per connection; `useSettingsSync` compares against them, then against what was applied on that connection (a restart drops the link, the next connection reads again). System services / characteristics / connectors are never removed, and the interface connector must stay on the link's characteristics.

**BLE settings Apply:** the board's own service (0xFFE0) is locked in firmware; user characteristics go in user services, and a characteristic is the board's only by its `system` flag (a board UUID elsewhere is a duplicate). New UUIDs are the first free ones. The board stages service / characteristic create / remove; the planner ends with `packet_settings_ble_apply_t`, which the board applies 200 ms after answering. Windows drops every GATT object of the device on the Service Changed that follows, so `sendSteps` waits 600 ms after apply and calls `session.refreshGatt()` (`adapter.reconnect()`: drop + re-open the link without the chooser, rediscover, re-attach notifications, session kept). Works with bleak on Windows; **in Chrome the reconnect still fails** (PROGRESS).

**Project file:** Open / Save (Settings and Code views) write objects + settings together (`App.tsx`); each workspace also auto-saves to browser storage (`runit.project`, `runit.ble.profile`, `runit.connectors`, `runit.logs`). Terminal panel: Commands (`CommandConsole.tsx`) and Errors & logs (`DiagnosticsConsole.tsx`).

**Shared UI:** `app/docs/ui-architecture.md` maps the screen and reusable controls. Text buttons are `components/Button` (`variant` primary / danger / dashed, `size` sm / icon), toggle pills `ToggleChip`; settings groups are `Card` + `FormRow` / `FormGrid`; details titles `PanelHeader`; local storage goes through `hooks/useStorage` (never a bare `localStorage` try/catch). Use `components/Badge` for passive chips: default size for palette IDs and status, `size="compact"` for dense BLE property flags, `size="detail"` for inspector labels; choose a theme-backed `tone` (`number` for types, `info`/`success`/`warning` for status, `accent` for selection context). `caps` uppercases status text, `push` aligns a chip to the far edge, and `filled` marks a prominent accent label. `TypeBadge` uses the same base for exact type codes. Keep clickable chips as buttons with their own behavior, not as badges.

## Checking the UI

- **Render tests** (`*.render.test.tsx`): `renderToString` of every page / state, so a page that throws fails in `npm test`. React splits text around expressions (`100<!-- -->%`): build one string where a test matches text.
- **In a browser:** the owner's dev server usually runs on port 5180 (strict: a second `vite` fails, use the running one). Playwright from a scratch venv drives the installed Chrome: `p.chromium.launch(executable_path=r"C:\Program Files\Google\Chrome\Application\chrome.exe")` (no browser download; its profile is separate, the owner's storage is untouched). Preload state through localStorage before `reload()`: `runit.canvases`, `runit.devices`, `runit.canvas.snap`; theme `runit-shell-theme`. HTML5 drag and drop works with `page.drag_and_drop`.
- Shell: patches with quotes / `${…}` are written as Python files (Write tool) and run; bash heredocs break on them here.
