# Firmware architecture

How the components fit together. Each component's own `*.MD` holds its API and wire format; this file only links them. Paths are under `runit-esp/components/` (the parts not moved yet: `runit-esp-archive/components/`, SKILL.md "Component docs").

## 1. The idea

A plug-and-play board for hobbyists. The board exposes what it has (devices, contracts, the VM, records) as **commands** on one router; a client (the app, a test host, the board itself) builds and drives everything through them. Everything the board says comes back as **streams** in the same command shape. A user program is compiled off-device, uploaded as VM records, stored as a project and run by the VM. Nothing on the board decides on its own beyond safety: the error policy and the power manager.

## 2. Layers

| Layer | Components | May depend on |
|---|---|---|
| core | `utils`, `time`, `errors`, `router`, `router_queue` | ESP-IDF only (and earlier core) |
| sys | (`sys/bus/`: `sys_uart`; the I2C contract `sys_i2c` is in `runit-esp`) `sys_log`, `sys_event_stream`, `sys_watch`, `sys_device_remote`, `sys_ble`, `sys_event`, `sys_device`, `sys_io`, `sys_power`, `sys_hbridge`, `sys_power_manager`, `sys_actions`, `sys_project` | core, earlier sys |
| devices | `devices/device_<chip>` (one driver each), `devices/devices` | core, sys (the contracts they implement, `sys_i2c`, `sys_io` for pins) |
| vm | `vm_core`, then `vm_blocks` | core, sys; `vm_blocks` also the devices whose own ops it has a block for |
| app | `app/runit` (boot, wiring, board config), `main` (only `runit_start()`) | everything |

Rules:
- A lower layer never includes a higher one. Where it must call up, the higher layer **registers** a function at boot (§5), always from `runit`.
- Self-registration by constructor exists only for tables of types: device types (`SYS_DEVICE_TYPE_REGISTER`), block types (`VM_BLOCK_TYPE_DEFINE`), error tag maps (`ERR_MODULE_DEFINE`). Those components are linked `WHOLE_ARCHIVE`.
- Declare only real dependencies in CMake (`REQUIRES` / `PRIV_REQUIRES`).

## 3. Boot

`runit_start()` runs the boot steps in order: RUNIT.MD "Boot" (nvs, session, streams, log, actions and events, watches, remote devices, lvgl, power, router, vm, the providers (uart, ble link), stream bindings, sessions, board at start, ble, project). A failing step is reported and the boot goes on; the last line is `runIT up (N boot step(s) failed)`.

## 4. Flows

- **Inbound command:** a provider's driver (`provider_console`: COBS + CRC16 frames on the console; `provider_ble`: the runIT RX characteristic) sends a whole frame out of its port; the session's port (SYS_SESSION.MD "The ports") takes it: a REQUEST `[type][src][key][seq u16][dir][code]...[payload]` (CMD.MD "The header") goes out of its sub-port `MODULE_ID_ROUTER` to the router's port (ROUTER_QUEUE.MD) → urgent or work task → root key → the module's router → its API → the answer `[ANSWER, status][key][seq][data]` back to the port it came from, which puts this board's id as `src` and sends it onto the line. The board's own commands: `router_inject` (src 0xFE); its calls to another board: `router_request` to that board's session (`sys_session_port`). `dir` picks the command's read or write side; a command with both is a mirror (the read answers what the write takes, CMD.MD "Read and write").
- **Streams:** a stream is a module's port of the data matrix, named by its module number, each packet `[hdr PUSH, key][data]` (DATA_MATRIX.MD): `LOGS` (0x2A, the log lines as text, out) and `ERRORS` (0x31, this board's records out, other boards' in and passed on, SYS_LOG.MD), `EVENTS` (0x25, the notify events out, other boards' in: published without NOTIFY and passed on, SYS_EVENT_STREAM.MD). Where a stream goes is its links: to a session's sub-port of that module (a PUSH to its peer, SYS_SESSION.MD), to a raw provider (the bytes as they are: the BLE logs), from a slave's session's sub-port in. A port that passes on what it takes sends it everywhere but back where it came from (`data_matrix_send_except`).
- **Providers:** one way bytes go out and come in (a UART port: the console's, the link's, or one the UART router makes, framed or raw; the runIT BLE pair, a user BLE characteristic). Each provider is a stream port (`core/data_matrix/data_matrix.h`): what comes in on its line goes out of its port to the ports linked from it, what its port takes is sent on its line (NOWAIT). Who reads it is only what is linked to it in the switch (SYS_DATA_PROVIDER.MD "Stream port", DATA_MATRIX.MD).
- **Sessions and the dead-man:** each side of a session says its own id in its HELLO (a board its place in the project, a client one of 0xF0..0xFC (the app takes 0xF0); two sessions with one id: `ERR_SESSION_ID_TAKEN`), the session opens when both hellos have passed and is kept with PINGs; a session that ends (silence, its provider down) makes its peer gone: its subscriptions end, and an armed dead-man enters the safe state (SYS_SYSTEM.MD).
- **One shape both ways:** stream payloads are commands without `dir`: an event is `[0x07][NOTIFY]...`, VM telemetry is `[0x0B][DATA | ADD_OBJECTS]...`, an error record carries the request that failed (with its `dir`). A client parses everything with one decoder, and a frame can be sent back as a write (`dir` 1 after the key) or stored in a record.
- **Errors:** a chain (ERRORS.MD) is returned up to whoever ends it; `err_report` → the sink in `runit_error_policy.c` → the device error policy (`sys_device_handle_error`, SYS_DEVICE.MD "Error policy") → an error record on the errors stream (ERRORS.MD "Error record"). Errors of a routed command are answered and reported with that command.
- **Events:** a source publishes (`sys_event_publish`, SYS_EVENT.MD): NOTIFY events go to the events stream first, then the device listeners (inline, their ON_EVENT), then the function listeners in the event task (the VM's wildcard subscription, the power manager). A device's `suspended` flag changing (SUSPEND, RESUME, a sweep: one event for the sweep) or a RESET that worked is the DEVICE contract's `SUSPENDED` / `RESUMED` / `RESET`: `sys_device` tells the state listener runit sets, which publishes it (SYS_DEVICE.MD "Suspended, resumed, reset").
- **Other boards:** a board's sessions form a star, one level deep (the root with its clients and children; a child has only its parent). Every board runs the same firmware and attaches the same sessions; the role is the hello's: a board's hello on the console's UART (another board's link wired to it) or on its runIT BLE pair (another board linked to it as a BLE central, SYS_BLE.MD "Central") makes that board the master, and the board's other sessions end while it lasts. A root's way to a child is its link UART or a BLE link (BLE CONNECT, then SESSION ATTACH as SLAVE; the app's project keeps them as the record `SYS_ACTIONS_ID_LINKS`). Id 0 is no id given yet: a root that takes children has another. A root programs the board on its link through that chip's ROM bootloader (`sys_flasher`, SYS_FLASHER.MD: its own firmware, then the child says hello with id 0); later updates of the child are OTA through the root. A frame for another board is forwarded by its `dst` on the driver's RX task, without the router, and only by the root between a client and a child (a child relays nothing, and the root never from a child to a child: `ERR_SESSION_NO_ROUTE`). The board's own call to another board (the router's `router_request` to the port `sys_session_port` gives, ROUTER_QUEUE.MD "Calls") keeps a slot in the router until the answer, its timeout or the session ending; a broadcast goes up to the root and down to every board. A lost peer is told to every listener, and by GONE from the root to every board (SYS_SESSION.MD). A peer that wants another board's stream subscribes there itself; the frames come back by their `dst`. Data can also be addressed to a provider of another board (SYS_SESSION.MD "Data to a provider"): a stream's remote target, a tunnel between boards, a client writing a child's UART.
- **Watches:** a peer's ADD (`MODULE_ID_WATCH`) names a read, a trigger and a period; `sys_watch` injects that read as a command of the board on its tick and sends each answer as an entry `[hdr PUSH, MODULE_ID_WATCH][owner][id][status][data]` out of its port `WATCH` to its links (the console's session, the raw BLE telemetry; a taker keeps its own by `owner`), from the router's work task (SYS_WATCH.MD). The peer's session ending removes its watches. The other way, this board's watches on other boards and its reads of them (`sys_watch_remote_add`, the cached `sys_watch_read`) go through the watch client.
- **Devices:** `[0x05][dir][id u16][op u16][args]` → `sys_device_call` → the driver's op table; contract ops are `0xCCxx` (contract ID, op), a driver's own ops `0xFFxx` (SYS_DEVICE.MD, SYS_IO.MD, SYS_POWER.MD, SYS_HBRIDGE.MD, SYS_DISPLAY.MD, SYS_TOUCH.MD). An op flagged local in its contract table (`SYS_DEVICE_OP_LOCAL`: the display's FLUSH) runs only from C; the router and a remote device refuse it (`ERR_DEV_LOCAL_OP`). A device of another board is a **remote device** (`CREATE_REMOTE`), a local alias: the registry keeps its type and where it is, and `sys_device_call` hands the call to sys_device_remote's hook, which sends that board's device command with the id swapped: waited for on a wired neighbour (`WIRED`), else a write not waited for and a read from a copy a watch on that board keeps. Its events and errors come by a subscription to the device on its board (REMOTE key 0x10, channel 0x81) and are published and reported as the local id's (SYS_DEVICE_REMOTE.MD).
- **Records and projects:** any command frame can be stored in a record (SYS_ACTIONS.MD) and run later. A project is a stream of such frames saved as records, loaded or run at a boot as its boot option says (`sys_project_boot_e`: none / load / run, SYS_PROJECT.MD). Settings are records of a module's write frame; nothing else replays by itself.

## 5. Wiring (all in `app/runit`)

| What | Where |
|---|---|
| Module routers under their root keys, the safe-state handler | `runit.c` (boot step `router`) |
| Error sink, device policy action runner, VM stop on a critical device error (`vm_stop_on_fault`) | `runit_error_policy.c` (`runit_error_wiring_init`) |
| Which stream goes to which provider (logs → BLE LOGS); the clients' sessions (UART, BLE pair) | `runit_board_cfg.c` (`runit_board_stream_bindings_init`), `runit.c` (`sessions_init`) |
| Power layout and limits for the power manager | the board's profile (`SYS_BOARD.MD`, LAYOUT and RAIL of `SYS_POWER_MANAGER.MD`), `board.json` |
| Onboard devices, their IDs and the I2C buses | the board's profile (`SYS_BOARD.MD`), `board.json`; the wiring as C in `runit-esp-archive/boards/` |
| The firmware's own actions (resume / suspend / reset all, hard reset) | `k_onboard` in `sys_actions.c` (`SYS_ACTIONS_ONBOARD_*`) |
| Safe state: VM stopped (retained values saved), then every device suspended | `runit_enter_safe_state` (`sys_system`: STOP, the dead-man; critical errors) |

## 6. Descriptors

Every contract, device, block, error map and the board have a JSON descriptor next to their code, written against `templates/*.schema.json` (templates/AGENTS.md). `sh templates/sync.sh` regenerates `enums.json`, `errors.json` and the limits from the C sources, validates every descriptor, checks it against the code (IDs, sizes) and publishes to `runit-app/generated/`, which the app reads. Wire-visible changes in C always go with a sync.
