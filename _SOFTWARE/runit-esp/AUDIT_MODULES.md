# Przegląd modułów `runit-esp` — duplikaty, nieścisłości i kandydaci do `core`

Audyt obejmuje wszystkie komponenty w `runit-esp/components/{core,sys,providers,devices}` oraz powiązane kontrakty JSON. Raport dzieli znaleziska na 4 kategorie (od najbardziej bezpośrednich zysków po większe porządki architektoniczne).

---

## 1. Zdublowane błędy (kandydaci do `core_errors.h` / ujednolicenia) — ✅ ZROBIONE

> **Status:** Skonsolidowano do `core_errors.h` (`ERR_BAD_ARG`, `ERR_NO_MEM { u32 size }`, `ERR_FULL { u16 max }`, `ERR_BUSY`, `ERR_BAD_OFFSET { u32 got, want }` + aktywowano `ERR_RANGE`). Usunięto 2 zbędne moduły błędów (`data_matrix_errors.h`, `sys_log_errors.h`), dodano węzły kontekstowe `ERR_BLE_UUID` i `ERR_PROV_ID` (zero utraty informacji), przemianowano `ERR_PROV_EXISTS` → `ERR_PROV_ID_TAKEN` (severity `ERR_PROV_SYSTEM` wyrównane do `MEDIUM`), dodano `ERR_PWRM_RAIL_TAKEN` zamiast nadużywanego `ERR_PWRM_BAD_ARG`. Katalog spadł do **18 modułów / 129 tagów (0 luk)**. Celowo pozostawiono domenowe `*_NOT_FOUND`, `*_UNKNOWN_OP` i `*_TAKEN` ze względu na bezpieczeństwo `err_drop()`/`err_root_tag()` oraz `id_kind` w UI.

System błędów w `runit-esp` buduje łańcuchy (`err_wrap`), więc kontekst modułu / ID urządzenia / klucza routera już znajduje się wyżej w łańcuchu. Mimo to większość modułów definiuje własne kopie tych samych generycznych błędów.

| # | Kategoria | Powtórzenia | Szczegóły i niespójności | Rekomendacja |
|---|---|---|---|---|
| **1.1** | **`BAD_ARG`** | **10 modułów** | **8 identycznych pustych `{}`**: `ERR_CMD_BAD_ARG`, `ERR_DATA_MATRIX_BAD_ARG`, `ERR_NVS_BAD_ARG`, `ERR_I2C_BAD_ARG`, `ERR_UART_BAD_ARG`, `ERR_ACTION_BAD_ARG`, `ERR_DEV_BAD_ARG`, `ERR_EVENT_BAD_ARG` (przy czym `ERR_NVS_BAD_ARG` ma `SEV_MEDIUM`, a pozostałe 7 `SEV_HIGH`). Dodatkowo `ERR_PWRM_BAD_ARG { value, min, max }` jest kopią `ERR_RANGE`, a `ERR_WATCH_BAD_ARG { u8 id }` ma `SEV_MEDIUM`. | Dodać ogólny `ERR_BAD_ARG` w `core_errors.h` i zastąpić `ERR_PWRM_BAD_ARG` istniejącym `ERR_RANGE`. |
| **1.2** | **`RANGE` (nieużywany w `core`!)** | **3 moduły** | `core_errors.h` definiuje już `ERR_RANGE { int32_t value; int32_t min; int32_t max; }` oraz `ERR_RANGE_F`, ale **0 plików produkcyjnych `.c` ich używa**. Zamiast tego `sys_power_manager_errors.h` ma `ERR_PWRM_BAD_ARG` o **identycznym payloadzie**, a `sys_device` definiuje `ERR_DEV_RANGE { u8 id; i32 value; i32 min; i32 max; }` (choć wywołania urządzenia i tak są owijane w `ERR_DEV_ID`). | Przełączyć `sys_power_manager` i `sys_device` na `ERR_RANGE` z `core_errors.h`. |
| **1.3** | **`NO_MEM`** | **4 moduły** | `ERR_ACTION_NO_MEM { u32 size }` (`HIGH`), `ERR_BLE_NO_MEM { u16 uuid; u32 size }` (`HIGH`), `ERR_PROV_NO_MEM { u8 provider; u16 size }` (`CRITICAL`), `ERR_DEV_NO_MEM { u8 id; u16 size }` (`CRITICAL`). Niespójna szerokość `size` (`u16` vs `u32`) i severity (`HIGH` vs `CRITICAL`). | Jeden `ERR_NO_MEM { uint32_t size; }` w `core_errors.h` (kontekst urządzenia/providera/UUID w łańcuchu lub opcjonalnym polu). |
| **1.4** | **`FULL`** | **12 modułów** | **6 identycznych pustych `{}` (`SEV_MEDIUM`)**: `ERR_DATA_MATRIX_FULL`, `ERR_ROUTER_CALLS_FULL`, `ERR_PROV_FULL`, `ERR_EVENT_TABLE_FULL`, `ERR_SESSION_FULL`, `ERR_WATCH_FULL`. Pozostałe 6 niosą konkretny limit/rozmiar (`ERR_CMD_OUT_FULL`, `ERR_ROUTER_TABLE_FULL`, `ERR_ROUTER_QUEUE_FULL`, `ERR_BLE_TX_FULL`, `ERR_REMOTE_SUBS_FULL`, `ERR_EVENT_QUEUE_FULL`). | Skonsolidować puste błędy wyczerpania tablicy slotów do jednego `ERR_FULL` w `core_errors.h` (zostawić wyspecjalizowane z payloadem `need/cap` lub kolejkowe). |
| **1.5** | **`NOT_FOUND`** | **8 modułów** | `ERR_NVS_NOT_FOUND {}` (`LOW`), `ERR_BLE_NOT_FOUND { u16 uuid }`, `ERR_I2C_DEV_NOT_FOUND { u8 bus; u8 addr }`, `ERR_ACTION_NOT_FOUND { u32 id }`, `ERR_PROV_NOT_FOUND { u8 provider }`, `ERR_DEV_NOT_FOUND { u8 id }`, `ERR_EVENT_NOT_FOUND { u16 id }`, `ERR_WATCH_NOT_FOUND { u8 id }`. | Jeśli UI (`errors.json`) nie potrzebuje osobnego `id_kind` per typ zasobu, można użyć wspólnego `ERR_NOT_FOUND` (z dyskryminatorem `kind` + `id_kind_by` w `errors_core.json`) lub zostawić tylko specyficzne (`ERR_I2C_DEV_NOT_FOUND`). |
| **1.6** | **`BUSY`** | **5 modułów** | Puste `{}` (`SEV_MEDIUM`): `ERR_ROUTER_BUSY`, `ERR_ACTION_BUSY`. Z payloadem: `ERR_I2C_BUS_BUSY`, `ERR_UART_BUSY` (`SEV_LOW`), `ERR_DEV_BUSY { id, op }`. | Puste `BUSY` scalić do `ERR_BUSY` w `core_errors.h`. |
| **1.7** | **`TAKEN` / `EXISTS`** | **6 modułów** | Niespójne nazewnictwo tego samego błędu kolizji ID: `ERR_PROV_EXISTS` vs `ERR_DEV_ID_TAKEN` vs `ERR_SESSION_ID_TAKEN` vs `ERR_ROUTER_KEY_TAKEN` vs `ERR_BLE_UUID_TAKEN` vs `ERR_I2C_ADDR_TAKEN`. | Ujednolicić do jednego `ERR_ALREADY_EXISTS` / `ERR_TAKEN` w `core` (z dyskryminatorem `kind` lub zostawić spójne nazwy). |
| **1.8** | **`OFFSET`** | **2 moduły** | `ERR_NVS_OFFSET { u32 got; u32 want; }` vs `ERR_ACTION_OFFSET { u16 got; u16 want; }` — ten sam błąd protokołu chunked write, różna szerokość intów. | Jeden `ERR_BAD_OFFSET { uint32_t got; uint32_t want; }` w `core_errors.h`. |
| **1.9** | **Lustrzane pary `PROV_*` vs `DEV_*`** | **2 moduły** | `ERR_PROV_SYSTEM` (`SEV_LOW`) vs `ERR_DEV_SYSTEM` (`SEV_MEDIUM`); `ERR_PROV_TYPE_UNKNOWN { u8 }` vs `ERR_DEV_TYPE_UNKNOWN { u16 }`; `ERR_PROV_UNKNOWN_OP { u16 }` vs `ERR_DEV_UNKNOWN_OP { u16 }` vs `ERR_ROUTER_UNKNOWN_OP { u8 }`. | Wyrównać severity (`SYSTEM`) i przenieść wspólne `ERR_UNKNOWN_OP` / `ERR_PROTECTED` do `core_errors.h`. |
| **1.10** | **Prawie martwe błędy w `core_errors.h`** | **1 użycie** | `ERR_NULL_PTR` jest użyte w dokładnie jednym miejscu (`err_record.c:93`), podczas gdy pozostałe moduły dla `NULL` rzucają `ERR_*_BAD_ARG`. `ERR_RANGE` i `ERR_RANGE_F`: **0 użyć**. | Konsekwentnie używać `ERR_NULL_PTR` i `ERR_RANGE` albo posprzątać nieużywane tagi. |

## 2. Zdublowane `#define`, makra i sentinele

| # | Problem | Lokalizacje | Opis |
|---|---|---|---|
| **2.1** | **Podwójna definicja `MUST_USE`** | `core/errors/errors.h:16-18`, `core/utils/utils.h:41` | W `errors.h` jest `#ifndef MUST_USE`, ale w `utils.h` `#define MUST_USE` **nie ma guarda `#ifndef`** — włączenie `errors.h` przed `utils.h` generuje warning redefinicji. |
| **2.2** | **`MSEC()` vs `pdMS_TO_TICKS()`** | `core/utils/utils.h:51` vs `core/timer/board_timer.c`, `sys/sys_device/slots/sys_device_slots.c`, `sys/sys_power_manager/sys_power_manager.c` | `MSEC(ms)` powstało, żeby krótkie timeouty nie zaokrąglały się w dół do `0` ticków. 8 modułów używa `MSEC()`, ale 3 nadal wołają gołe `pdMS_TO_TICKS()`. |
| **2.3** | **`TICK_MS = 10u` powtórzone 3×** | `core/router_queue/router_request.c`, `sys/sys_session/sys_session.c`, `devices/virtual/device_dc_motor/device_dc_motor.c` | Identyczna lokalna stała `TICK_MS 10u` definiowana w każdym pliku osobno. |
| **2.4** | **Brakujące stałe w C, które opisuje JSON** | `sys/sys_data_provider/router/contract_provider.json` vs `sys/sys_data_provider/router/sys_data_provider_router.c` | Kontrakt JSON odwołuje się do `SYS_DATA_PROVIDER_ID_NONE` (`0xFF`) oraz `SYS_DATA_PROVIDER_CREATE_SYSTEM` (`0x01`), ale żadna z nich nie jest zdefiniowana w publicznym nagłówku C (`CREATE_SYSTEM` jest prywatnym `#define` w `.c`). Dla porównania `sys_device.h` eksportuje `SYS_DEVICE_ID_NONE` i `SYS_DEVICE_CREATE_SYSTEM`. |
| **2.5** | **Niespójny sentinel „brak urządzenia” (`0xFF` vs `0xFFFF`)** | `sys/sys_device/sys_device.h` vs `sys/sys_power_manager/sys_power_manager.h` | Cały `sys_device` ma ID typu `uint8_t` i sentinel `SYS_DEVICE_ID_NONE = 0xFF`. Tymczasem `sys_power_manager` używa `uint16_t` i `0xFFFF` (`NO_DEV` / `TARGET_BOARD`), mimo że event `PWRM_EV_LIMIT_REACHED` używa już `uint8_t device`. |
| **2.6** | **Rozproszone sentinele `0xFF`** | `core/data_matrix/data_matrix.c:21` (`NO_PORT`), `ESP32S3_GPIO_PWM_TIMER_NONE`, `SYS_IO_PIN_NONE_INDEX`, `SYS_POWER_PD_TYPE_NONE`, `CMD_SRC_ALL` | Warto ujednolicić konwencję nazewniczą (`*_NONE` zamiast `NO_*`). |
| **2.7** | **Nieaktualne hex ID w komentarzach/dokumentacji po renumeracji** | m.in. `sys/bus/sys_ble/router/sys_ble_router.h:12` (`0x2E` zamiast `0x2D`), `sys/sys_data_provider/router/contract_provider.json:10` (`0x0D` zamiast `0x2B`), `sys/sys_data_provider/AGENTS.md` | Po renumeracji `MODULE_ID_*` część komentarzy i opisów nadal cytuje stare wartości hex. |

## 3. Powtarzające się mechanizmy i funkcje pomocnicze

| # | Mechanizm | Gdzie się powtarza | Co można wydzielić / uprościć |
|---|---|---|---|
| **3.1** | **Czyszczenie ringbuffera i kontrola rezerwy `CMD_SEND_SPARE`** | `sys/bus/sys_ble/sys_ble.c`, `sys/bus/sys_uart_contract/sys_uart_codec.c`, `devices/soc/device_esp32s3_uart/device_esp32s3_uart.c` | Identyczna pętla opróżniania ringbuffera powtórzona 3×. Rezerwacja połowy bufora dla `CMD_SEND_SPARE` zaimplementowana inaczej w UART (`ITEM_BYTES` + `ring_used`) niż w BLE (`vRingbufferGetInfo`). Kandydat na `u_ringbuf_clear()` / `u_ringbuf_used()` w `core/utils/`. |
| **3.2** | **Ręczne `xSemaphoreTake`/`Give` mimo gotowego `U_MUTEX_GUARD`** | `U_MUTEX_GUARD` w `core/utils/utils.h` używany w 4 modułach, natomiast ręczne pary lub lokalne `lock()/unlock()` w 9 plikach: `nvs_store.c`, `sys_ble.c`, `sys_actions.c`, `sys_device_remote.c`, `sys_watch.c`, `sys_watch_client.c`, `device_esp32s3_gpio.c`, `device_esp32s3_uart.c`, `sys_device_slots.c` | Przełączyć proste sekcje na `U_MUTEX_GUARD` oraz dodać `U_CRIT_GUARD(&mux)` dla `portENTER_CRITICAL`/`portEXIT_CRITICAL` (~10 plików). |
| **3.3** | **Boilerplate subskrypcji `SESSION_GONE_FILTER`** | `sys_device_remote.c`, `sys_system.c`, `sys_watch.c`, `sys_watch_client.c` | 4 moduły powtarzają ten sam kod subskrypcji `SESSION_GONE_FILTER` (`SYS_EVENT_RUN_INLINE`) i rozpakowania `source` + `evt_data_SESSION_EV_GONE_t`. Można dodać helper `sys_session_on_gone(fn, ctx)` w `sys_session`. |
| **3.4** | **Składanie i wysyłanie ramki `CMD_PUSH`** | `sys_log.c`, `sys_event_stream.c`, `sys_watch.c`, `sys_device_remote.c` | Każdy moduł ręcznie rezerwuje bufor `CMD_HEAD + payload`, woła `cmd_push_head(...)`, kopiuje payload i woła `data_matrix_send(...)`. Mały helper uprości 4 miejsca i wyeliminuje VLA z `sys_event_stream.c`. |
| **3.5** | **Podwójny wzorzec rejestru typowanego** | `sys_device` vs `sys_data_provider` | Oba implementują tablicę slotów, per-slot mutex z konstruktora, autorejestrację sterowników (`*_TYPE_DEFINE`), komendy `0xFFxx` i flagę `SYSTEM`, ale z rozjechanymi detalami API i błędów. |

## 4. Nieścisłości implementacyjne między podobnymi modułami

| # | Obszar | Rozbieżność | Pliki |
|---|---|---|---|
| **4.1** | **Cykl inicjalizacji (`constructor` vs `*_init()`) i idempotentność** | Część modułów używa `__attribute__((constructor))` (`router_queue`, `sys_data_provider`, `sys_device_remote`), część jawnych `*_init()` w `runit_start()`, a `sys_device_remote` obu naraz. Część `*_init()` jest idempotentna (`sys_device_policy_init`, `sys_actions_init`), a inne zawodzą przy drugim wywołaniu (`sys_log_init`, `sys_event_stream_init`). | `router_queue.c`, `sys_data_provider.c`, `sys_device_remote.c`, `sys_log.c`, `sys_event_stream.c` |
| **4.2** | **Dispatch routera (`sys_data_provider_router` vs `sys_device_router`)** | `sys_device` deklaruje operacje publicznie przez `CONTRACT_SYS_DEVICE_OPERATIONS` w `sys_device.h`, a `sys_data_provider_router.c` nie używa `CMD_TABLE_DECLARE` i trzyma prywatne `#define CONTRACT_PROVIDER_OP_*` w `.c`. | `sys_device_router.c`, `sys_data_provider_router.c` |
| **4.3** | **Szerokość ID urządzenia w `sys_power_manager`** | `sys_power_manager` używa `uint16_t` (`0xFFFF`) zamiast `uint8_t` (`SYS_DEVICE_ID_NONE = 0xFF`), mimo że jego własny event `PWRM_EV_LIMIT_REACHED` ma już `uint8_t device`. | `sys_power_manager.h`, `sys_power_manager_errors.h` |
| **4.4** | **VLA na stosie i brak checka `data_matrix_linked()` w `sys_event_stream`** | `sys_log.c` sprawdza `data_matrix_linked(&s_logs)` i używa stałego bufora, a `sys_event_stream.c` alokuje VLA `uint8_t packet[CMD_HEAD + len]` na stosie i kopiuje dane nawet bez podłączonych portów. | `sys_log.c`, `sys_event_stream.c` |
| **4.5** | **Obsługa błędów w tle: `err_free` vs `err_report`** | `provider_ble.c` i `sys_event_stream.c` po cichu robią `err_free(...)`, podczas gdy `sys_device_timer.c` i `sys_ble.c` zgłaszają błędy przez `err_report(...)`. | `provider_ble.c`, `sys_event_stream.c`, `sys_device_timer.c`, `sys_ble.c` |
| **4.6** | **Kolizja nazw dwóch plików `sys_device_remote.c`** | Dwa różne pliki źródłowe mają identyczną nazwę bazową: `sys_device/remote/sys_device_remote.c` i `sys_device_remote/sys_device_remote.c`. | `sys_device/remote/sys_device_remote.c`, `sys_device_remote/sys_device_remote.c` |
| **4.7** | **Statyczne `U_TASK_DEFINE` vs dynamiczne `xTaskCreate`** | Prawie wszystkie taski są statyczne (`U_TASK_DEFINE`), poza `sys_power_manager.c` i `device_esp32s3_uart.c` (`xTaskCreate` dla dynamicznego cyklu życia). | `sys_power_manager.c`, `device_esp32s3_uart.c` |
| **4.8** | **6 przestarzałych starych testów hostowych (nie kompilują się)** | Niezaktualizowane po refaktorze `router_submit` → `data_matrix`: `router_queue`, `sys_actions`, `sys_data_provider`, `sys_event_stream`, `sys_session`, `sys_watch`. | `*/host/test_*.c` i `host_test.json` |
